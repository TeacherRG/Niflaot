# Единый лексикон иврита: стандарт данных

## Цель

Танах и «Мишне Тора» — два корпуса употребления, а не два независимых словаря. У них общий лексикон, а различаются источники, контексты и морфологические разборы.

## Сущности и связи

- **Lexeme (лексема)** — единица словаря с устойчивым ID и одним лексическим значением. Омонимы с разными значениями получают разные ID.
- **Sense (значение)** — один смысл лексемы. Переводы ru/en/de принадлежат значению, а не словоформе.
- **Headword (заголовочная форма)** — нормативная форма для показа и поиска.
- **AttestedForm (засвидетельствованная форма)** — форма, реально встреченная в источнике, с исходным морфологическим тегом.
- **Occurrence (употребление)** — конкретное место в Танахе или «Мишне Тора» и форма слова именно в тексте.
- **Source (источник данных)** — корпус, версия разметки, лицензия и происхождение данных.

## Лингвистический стандарт заголовочной формы

1. Глагол показывается по инфинитиву конструкта (שם הפועל, infinitive construct), если он засвидетельствован и однозначно относится к данной лексеме.
2. Инфинитив абсолютный допустим как запасной вариант, только если инфинитив конструкта для лексемы не найден. Он обязательно помечается своим типом.
3. Нельзя механически добавлять ל к форме прошедшего времени и объявлять результат инфинитивом.
4. Если надёжная форма не установлена, запись получает статус review/unverified; приложение не должно выдавать догадку за норму.
5. Существительные, прилагательные и другие части речи сохраняют собственные словарные конвенции; правило инфинитива к ним не применяется.
6. Корень (שורש), лемма, словоформа и написание без огласовок — разные поля. Корень не заменяет заголовочную форму.
7. Огласовки сохраняются в заголовочной и засвидетельствованных формах. Удаление огласовок используется только для поиска, не для объединения лексем.

## Идентификаторы и объединение

- ID лексемы стабилен и не зависит от частоты или порядка загрузки. Для импортированных записей Танаха используется пространство `tanakh:strong:<id>`; для записей Рамбама — детерминированный технический ID. До редакторской проверки Rambam-ID считаются предварительными: различия переводов используются только как временный разделитель кандидатов, а не как доказательство разных значений.
- Strong's number хранится как внешний идентификатор источника, но не становится единственным внутренним ID.
- Совпадение букв без огласовок не является основанием для слияния.
- Слияние допустимо только при совпадении лексического значения и грамматической леммы; омонимы и разные значения разделяются.
- Старые пользовательские отметки обучения мигрируют через таблицу соответствия старых ID → новый Lexeme ID. Если соответствие неоднозначно, отметка не переносится автоматически и остаётся в отчёте миграции.

## Данные и ответственность

- Переводы ru/en/de хранятся раздельно от ивритского текста.
- Разные переводы одного значения — массив вариантов; контекстные пояснения не подменяют базовый перевод.
- Термины ґалахи — отдельные тематические определения/доменные пометы, связанные с соответствующим значением, а не отдельная параллельная статья.
- Частотность и рейтинг — метаданные конкретного корпуса, не свойства лексемы в целом; поэтому частота хранится в `corpusStats.tanakh` / `corpusStats.mishneh-torah`.
- Глоссарные термины ґалахи хранятся как структурированные аннотации значения (`terms`), отдельно от обычного перевода.
- Употребления Танаха и «Мишне Тора» отображаются как независимые источники присутствия.
- Каждая автоматически извлечённая форма хранит происхождение и исходный тег. Ручная правка также маркируется как manual.
- Лицензия и атрибуция фиксируются на уровне источника.

## Техническая миграция

Миграция проводится поэтапно, без одномоментного удаления старых файлов:

1. Вводится типизированная схема `src/core/hebrewLexicon.ts` и валидатор.
2. Создаётся канонический `src/tanakh/lexicon.json` (в дальнейшем его логичнее переместить в `src/lexicon/`), который содержит лексемы, значения, формы и источники.
3. Импортёры OSHB и Sefaria генерируют данные в эту схему; генераторы не принимают решение о слиянии омонимов по одним буквам.
4. Старые `words.json`, переводы Танаха и Rambam-словари временно становятся совместимыми представлениями (адаптерами) канонической базы.
5. UI и алгоритм повторения переводятся на Lexeme ID. Только после проверки миграции прогресса старые хранилища выводятся из эксплуатации.

## Критерии приёмки

- Нет повторяющихся ID.
- Каждая лексема имеет хотя бы одно значение.
- Нормализованное написание соответствует заголовочной форме.
- У записи, определённой как глагол, явно указан тип инфинитива либо запись отмечена как требующая проверки. Записи с неизвестной частью речи не получают выдуманную грамматическую метку.
- Каждое употребление содержит корпус, ссылку и реальную форму в тексте.
- Омонимы не объединяются автоматически по неогласованному написанию.
- Прогресс обучения не теряется и не объединяется между неоднозначными статьями.


## Прогресс слов: одна колода и одно хранилище

- «Мои слова» и «Слова ґалахи» используют одно хранилище `niflaot:words` и один формат записи `[время, коробка, день повтора]`.
- Для слов ґалахи ключи имеют префикс `h:`, чтобы не смешивать их с номерами Стронга до завершения перехода интерфейса на канонические Lexeme ID.
- При первом открытии раздела «Слова ґалахи» старое `niflaot:halacha-words` копируется в общую колоду. Для одинакового ключа сохраняется более позднее изменение.
- Старое хранилище не удаляется: оно остаётся резервной копией и продолжает синхронизироваться со старыми устройствами. Новые изменения пишутся только в `niflaot:words`.
- `niflaot:lashon` остаётся отдельным: это прогресс уроков, а не карточная колода слов.
- В следующем этапе ключи `h:` будут сопоставлены с каноническими ID по таблице лексикона. Никакого автоматического объединения по одному написанию нет.
